# Instagram ins01–ins10 browser workspace

The user has ten Instagram accounts and explicitly requested FB-style independent browser shortcuts and video folders. Numbering is ins01–ins10, with faithdjurner96 provisionally expected in ins01 and the other usernames pending registration. The user chose logged-in browser operation, not Meta developer/OAuth setup. Instagram uses independent videos, the exact existing FB caption and automatic first-comment text. This installer establishes folders and login entries only; it does not implement or enable publication.

Default Windows root is E:\IG-AutoUpload, separate from E:\FB-AutoUpload. Each slot has profiles\insXX and videos\insXX\inbox, published, review and failed. The shortcuts directory contains ten normal Chrome links (a unique --user-data-dir for each slot, no incognito and no shared FB profile) plus ten account inbox links. Two desktop folder shortcuts, Instagram账号 and Instagram素材, point to these entries and the video root. The actual Windows Desktop is obtained using Environment.GetFolderPath, including redirected desktops. No browser is launched by setup; users open slots individually and sign in normally. Existing login from another browser is not copied into a new profile.

The initial config names ins01's expected username but does not claim a verified browser identity; every slot has identity_verified=false and publishing_enabled=false. The editable registration CSV is a template, not automatic identity verification. Global original caption/comment files are created once and retained on replay. Future automation must verify the logged-in handle matches the chosen numbered slot before enabling uploads or commenting on an exact published media ID.

The setup rejects FB roots, malformed/foreign workspace registration, nonempty unclaimed profiles, linked/reparse paths and conflicting shortcuts. It records workspace ownership before creating partial state so interrupted installs can resume. A named Windows mutex prevents parallel installers. Existing login databases, videos, account mappings, manually edited content and enabled/verified configuration are preserved on rerun. WScript.Shell shortcuts are validated before writes; an unchanged owned link may be updated if the known Chrome executable location changes, but unrelated user shortcuts are not replaced. JSON data is passed through stdin rather than interpolated into PowerShell code.

Seven checks cover unique Chrome argument/profile binding (including spaces), all media directories and entry counts, original text, no publication enablement, rerun preservation of cookies/media/mappings/text, rejection of foreign FB roots and unclaimed/linked data, shortcut-conflict prevention, interrupted setup recovery and PowerShell syntax parsing. Cloud tests do not establish actual desktop creation; the user must run the pinned Windows command and provide its completion acknowledgment.
